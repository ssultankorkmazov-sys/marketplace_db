# MarketKZ: аудит и состояние миграции

Проверено: `src/`, `server/`, `db/marketplace_db.sql`, текущие тесты и документация. Каталог уже читает PostgreSQL через API. Остальные процессы на момент аудита опирались на `src/data/mock.ts` и локальное состояние. Браузерное хранение корзины и избранного само по себе не обеспечивает синхронизацию между устройствами и не считается серверной реализацией.

| Функция | Текущее поведение до этапа 1 | Необходимый API | Состояние миграции |
|---|---|---|---|
| Каталог, поиск, категории, карточка товара | PostgreSQL через существующий API; в тестах/опциональном dev-режиме есть локальный источник | Уже есть `GET /api/v1/products`, `/categories` | Подключено; существующий dev-only mock путь сохранён |
| Регистрация | Добавляла пользователя и пароль в `localStorage` | `POST /api/v1/auth/register` | Этап 1: серверная регистрация, scrypt-хеш, уникальные email/телефон |
| Вход и сессия | Демо-пароли и JSON-сессия в `localStorage` | `POST /auth/login`, `GET /auth/me`, `POST /auth/logout` | Этап 1: PostgreSQL-сессия; браузеру выдаётся HttpOnly cookie, в БД хранится только хеш токена |
| Профиль | Чтение/изменение локальной таблицы | `GET /auth/me`, `PATCH /profile` | Этап 1: чтение серверного профиля, изменение имени/телефона/адреса с проверкой владельца |
| Сброс пароля / существующие аккаунты | Нет безопасного восстановления; seeded пользователи использовали общий демо-пароль | Поток сброса с одноразовым токеном и подтверждением владения email | Не реализовано. Старые строки сохранены; `password_hash` у них пустой, старый демо-пароль отключён |
| Корзина | `localStorage` + React state | Для учебного MVP отдельный API не обязателен | Этап 2: остаётся клиентской, цены и наличие повторно загружаются из API каталога |
| Оформление заказа | Создавало заказ/позиции/платёж в localStorage; итог брался из клиентских цен | `POST /api/v1/orders` с транзакцией, блокировкой товара, серверным пересчётом и списанием остатка | Реализовано: заказ и позиции записываются атомарно; оплата только демонстрационная, статус Pending |
| История и детали заказов | Локальные таблицы; проверка владельца в UI | `GET /api/v1/orders`, `GET /api/v1/orders/:id` с владельцем в SQL | Реализовано: выдаются только заказы текущего пользователя; чужой заказ отвечает 404 |
| Избранное | `localStorage` (`favs`) | `GET/PUT/DELETE /favorites` | Этап 4 |
| Отзывы и рейтинг | Локальные отзывы и вычисляемые рейтинги | `GET/POST/DELETE /reviews`; авторизация и правила публикации | Этап 5 |
| Админ-панель: товары | До этапа 6 CRUD менял только localStorage; роль проверялась только UI | `GET/POST/PATCH/DELETE /api/v1/admin/products*`; роль проверяется на каждом endpoint | Реализовано: удаление блокируется внешними ключами при связанных заказах/отзывах |
| Админ-панель: список заказов | Использовал локальные таблицы; роль проверялась только UI | `GET /api/v1/admin/orders` | Реализовано для просмотра. Статус отображается без локальной имитации изменения |
| Админ-панель: категории/пользователи/отзывы | Чтение и CRUD из локальных таблиц | Защищённые admin API | Не реализовано; остаётся следующим этапом |
| Настройки/фильтры/шаги оформления | React state; фильтры сбрасываются при загрузке | API не нужен для краткоживущего UI-состояния; настройки могут оставаться локальными | Этап 7; нужно отделить предпочтения от бизнес-данных |

## Изменения этапа 1

- Добавлена аддитивная миграция `db/migrations/001_auth.sql`: `users.password_hash`, `users.role`, `user_sessions`. Она не удаляет и не пересоздаёт существующие таблицы.
- Существующие учётные записи не получили выдуманный пароль или привилегии. Для них нужен отдельный подтверждённый сброс пароля; пока они не могут войти.
- Для снимка доставки добавлена `002_order_delivery.sql`; старые заказы остаются с пустыми новыми полями и доступны для чтения.
- Демо-платёж создаёт запись со статусом `Pending`. Интеграции с платёжным оператором и списания средств нет.
- Для назначения администратора DBA должен вручную изменить роль конкретной проверенной учётной записи. Публичной регистрации с ролью admin нет.
- `src/data/mock.ts` остаётся тестовой/dev-фикстурой для ещё не мигрированных этапов; production fallback каталога не включён.
- Admin MVP endpoints читают актуальную роль из сессии и защищены backend-проверкой; роль выдаёт оператор локальной базы данных вручную.
- Существующие неподключённые сервисы остаются незавершёнными этапами, перечисленными выше.
