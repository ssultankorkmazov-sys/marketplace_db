# Выгрузка audit-событий и локальная псевдонимизация

## Перед началом

Эта инструкция не требует передавать кому-либо пароль, connection string, `.env` или доступ к Neon. В production выполняется только один read-only `SELECT`; он ничего не меняет. Выгрузка временно содержит настоящие `user_id`, поэтому CSV нужно хранить локально и не отправлять.

SQL выбирает только `user_id`, `action`, `created_at` в UTC и `status`. Поле `status` оставлено для проверки качества записей; Jeffreys Divergence сейчас использует только действие и время. IP, email, имена, телефоны, адреса, `details`, пароли и токены не выбираются.

## Экспорт через Neon SQL Editor

1. Самостоятельно войдите в [Neon Console](https://console.neon.tech/) обычным способом. Убедитесь, что выбраны нужный проект, production branch и база, содержащая `public.audit_logs`. Не копируйте credentials в чат, терминал или файлы проекта.
2. Откройте SQL Editor и загрузите [jeffreys-neon-export.sql](./jeffreys-neon-export.sql) из проекта либо скопируйте его текст.
3. Перед выполнением проверьте выбранный проект и базу в интерфейсе. SQL ограничен последними 180 днями и содержит только `SELECT`; не запускайте его повторно с расширенным диапазоном автоматически, если строк мало.
4. Выполните запрос и сохраните результат как CSV в закрытую локальную папку **вне репозитория**. Не открывайте и не пересохраняйте CSV в Excel/табличном редакторе: он может изменить timestamps или преобразовать идентификаторы.
5. Если результат пустой, слишком большой или покрывает меньше нужного периода, остановитесь и сообщите только безопасные агрегаты (число строк и диапазон дат). Не расширяйте окно без отдельного решения.

180 дней предусмотрены для разогрева baseline до 90 дней, калибровочного периода, отдельного holdout и временного запаса. Фактические границы калибровки и holdout необходимо зафиксировать после проверки доступного временного покрытия, но до просмотра значений divergence.

## Псевдонимизация локально

Из корня репозитория запустите локальный конвертер, указав пути к CSV и новому JSON-файлу вне проекта:

```powershell
node .\server\scripts\pseudonymize-jeffreys-export.mjs `
  --input-csv "C:\PrivateData\audit-export.csv" `
  --output-json "C:\PrivateData\jeffreys-events.json"
```

Скрипт проверяет точные заголовки CSV и значения, затем создаёт случайное отображение `user_id` в числовые псевдонимы **только в памяти**. Псевдонимы выбираются выше максимума PostgreSQL `INT`, поэтому ни один из них не равен исходному целочисленному `user_id`. Таблица соответствий не сохраняется, не выводится и очищается после конвертации. Если выходной файл уже существует, скрипт откажется его перезаписывать.

Результат — JSON-массив для локальной обработки со столбцами `user_id` (псевдоним), `action`, `created_at`, `status`. Неизвестные названия действий заменяются на `__UNKNOWN_ACTION__`; событие остаётся в наборе и по-прежнему попадает в категорию `OTHER`. Для отдельного манифеста временных границ используйте формат из [jeffreys-historical-import-format.md](./jeffreys-historical-import-format.md); не сохраняйте в нём исходные ID.

## Проверки и удаление исходной выгрузки

- Скрипт сообщает только число событий, число псевдонимов, число событий без пользователя и UTC-диапазон; реальные ID не печатаются.
- JSON содержит только четыре разрешённых поля. `user_id` в итоговом файле должен быть `null` или числом выше диапазона PostgreSQL `INT`; неизвестные action names не сохраняются дословно.
- Не публикуйте ни CSV, ни JSON: действия и timestamps всё ещё могут раскрывать поведенческие сведения, даже после удаления прямых идентификаторов.
- После локальной проверки удалите исходный CSV и не добавляйте ни один из файлов выгрузки в Git. Храните обезличенный набор только столько, сколько требуется для калибровки.

## Перед реальной calibration/holdout оценкой

Полученный JSON ещё нельзя напрямую использовать для вывода о пороге. Текущий replay study script пока не читает временной манифест и не разделяет calibration/holdout. Перед расчётом потребуется изменить offline study так, чтобы порог определялся только на calibration-периоде, затем был зафиксирован и применён один раз к holdout. Не подключайте этот набор к worker и не создавайте incidents.
