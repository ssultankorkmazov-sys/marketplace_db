# Безопасный формат исторических событий для Jeffreys replay

## Состояние источников

В репозитории нет выгрузки исторических `audit_logs`. Файл `jeffreys-replay-results.json` содержит только синтетические данные и не является источником калибровки. На момент аудита `TEST_DATABASE_URL` не настроен. Данные из `.env`, production или Neon для подготовки этой спецификации не читались.

## Файлы набора

Подготовьте один JSON-файл с хронологией и отдельный JSON-манифест с границами временного разделения. В наборе должна быть вся временная последовательность целиком: псевдоним пользователя должен быть одинаковым в calibration и holdout.

Форма одного события, совместимая с текущим `ReplayAuditEvent`:

```ts
interface Event {
  user_id: number | null; // стабильный положительный псевдоним, не исходный users.user_id
  action: string;         // audit action; неизвестные действия учитываются как OTHER
  created_at: string;     // ISO 8601 в UTC
  status?: 'SUCCESS' | 'FAILURE'; // сохраняется для аудита качества; текущая метрика его не использует
}
```

Текущий CLI принимает JSON-массив таких событий через `--input`. Для этого режима текущий файл должен содержать именно массив, а не объект-обёртку. Время в данных должно включать достаточно истории до начала scoring, чтобы построить baseline до 90 дней.

Манифест рядом с набором должен содержать:

```ts
interface Manifest {
  formatVersion: 1;
  timezone: 'UTC';
  calibrationStartInclusive: string;
  calibrationEndExclusive: string;
  holdoutStartInclusive: string;
  holdoutEndExclusive: string;
  exportedEventCount: number;
  sourceDescription: 'separate_test_database' | 'approved_anonymized_export';
}
```

Это описание формата, не готовые данные. Даты и количество должны быть заполнены по фактической выгрузке. Для holdout первая оцениваемая current window должна целиком находиться после `holdoutStartInclusive` (отступ минимум 24 часа при текущей сетке окон). Baseline holdout может использовать только события, предшествующие соответствующему окну. Порог выбирается только по calibration; holdout используется один раз для независимой оценки.

## Псевдонимизация и минимизация данных

- До передачи файла замените каждый исходный user ID стабильным случайным целым числом в пределах безопасного целочисленного диапазона. Назначайте отображение в памяти для всей объединённой хронологии, затем уничтожьте mapping. Не сохраняйте и не передавайте таблицу соответствия.
- Если псевдонимизация выполняется несколькими выгрузками, используйте одну и ту же локальную mapping-сессию для обеих временных частей; безопаснее сформировать единый набор и разделить его по времени при replay.
- В набор не включайте `ip_address`, email, имена, телефоны, адреса, пароли, токены, `details`, содержимое заказа или иные поля, не перечисленные в форме события.
- События с `user_id = null` допустимы в файле, но текущий replay не включает их в персональные baseline и оценки.
- Убедитесь, что каждая строка исходного аудита включена не более одного раза. Не фильтруйте события по их будущему результату и не удаляйте неизвестные actions: их можно заменить безопасным sentinel `__UNKNOWN_ACTION__`, который попадёт в `OTHER`.
- Не отправляйте файл через Git, не добавляйте его в репозиторий и удалите временные файлы выгрузки после проверки.

## Что нужно проверить до расчёта

1. Источник — только отдельная тестовая база или отдельно одобренная обезличенная выгрузка; не используйте `DATABASE_URL` из `.env`.
2. Подтвердите фактический диапазон дат, общее число событий, число уникальных псевдонимов и покрытие по дням. Эти агрегаты не должны содержать идентификаторы.
3. Проверьте корректность UTC timestamps, повторов и полноту временного диапазона. Не публикуйте action-count таблицы для малых групп, если они могут раскрыть поведение конкретного пользователя.
4. Зафиксируйте временные границы до просмотра holdout-результатов.

## Ограничение текущего инструмента

Существующий `jeffreys-replay-study.mjs --input` принимает события, но пока не читает манифест, не отделяет временные calibration и holdout периоды и не переносит порог, выбранный на calibration, на holdout. До оценки реальной holdout-частоты потребуется отдельное изменение study script: добавить явное временное разделение, калибровку порогов только на calibration-срезе и применение зафиксированного порога к holdout-срезу. Сам `jeffreysReplay.ts` уже способен считать хронологические окна без использования будущих событий.
